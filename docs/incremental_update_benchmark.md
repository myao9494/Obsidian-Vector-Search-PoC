# ファイル変更差分更新 ベンチマーク検証＆最適化レポート

## 1. 概要
ファイル監視によってファイルの作成・変更・削除が検知された際、システムが「変更差分の分だけモデルのアップデート（Embedding生成＆インデックス更新）」を行うのにどの程度の時間を要するかを検証・計測しました。

---

## 2. 実測ベンチマーク結果（実測値）

### 測定環境
* **OS**: macOS (Metal GPU / MPS アクセラレーション)
* **Embedding モデル**:
  * ⚡ **超軽量モデル**: `ruri-v3-30m` (256次元, 30M パラメータ)
  * 👑 **標準モデル**: `ruri-v3-310m` (768次元, 310M パラメータ)

### シナリオ別 処理所要時間一覧表（ミリ秒）

| テストシナリオ | 状態 | チャンク数 | `ruri-v3-30m` (超軽量) | `ruri-v3-310m` (標準) |
| :--- | :--- | :---: | :---: | :---: |
| **1. 日常的小規模修正** (1行改訂 / Typo修正) | `updated` | 3個 | **27.69 ms** | **96.49 ms** |
| **2. 中規模加筆** (2セクション追加 / 1,200字) | `updated` | 5個 | **51.75 ms** | **167.89 ms** |
| **3. 長文ノート作成** (9セクション / 3,500字) | `created` | 9個 | **84.76 ms** | **373.24 ms** |
| **4. 変更なしスキップ判定** (ハッシュ比較) | `skipped` | 0個 | **0.39 ms** | **0.30 ms** |
| **5. ファイル削除検知 & DB削除** | `deleted` | 0個 | **0.63 ms** | **0.44 ms** |
| **6. 意地悪テスト** (超長文1.2万字 + 特殊記号) | `created` | 39個 | **420.84 ms** | **4,300.40 ms** |

## 3. 処理工程別の内訳とボトルネック分析

1ファイル更新時の処理時間内訳は以下の通りです。

```
[ファイル変更検知]
  │
  ├─ 1. I/O & SHA-256ハッシュ計算  :  0.05 〜 0.15 ms  (0.2%)
  ├─ 2. Markdown解析 & チャンキング :  0.06 〜 0.73 ms  (0.5%)
  ├─ 3. Embedding生成 (モデル推論) : 26.0 〜 418.0 ms  (97.5% ★最大ボトルネック)
  └─ 4. SQLite保存 & FAISS反映    :  0.80 〜 1.30 ms  (1.8%)
  │
[検索可能状態]
```

### 主要な知見
1. **日常的な修正は ~30ms（超軽量）/ ~100ms（標準）で完了**:
   * 人間の体感認識速度（約100〜200ms）を下回っており、ユーザーが編集して即座に検索しても遅延を感じないレベルです。
2. **ボトルネックの95%以上は Embedding 推論**:
   * I/O、チャンキング、SQLiteトランザクション、FAISSインデックス更新はいずれも1ミリ秒未満で完了しており、極めて高速です。
3. **意地悪テスト（1.2万文字）への耐性**:
   * 39チャンクに及ぶ超長文・特殊記号乱舞のノートであっても、クラッシュすることなく安全にインデックス化が完了しました。

## 4. GUI ライブ検証機能の使い方

画面中央の「⚡ ファイル差分更新・ライブ時間検証」パネルからリアルタイムに実験が可能です。

1. **ファイルパス指定**:
   * 対象ファイル相対パス（例: `社内経費精算ガイド.md` や `test.md`）を入力。
2. **直接編集 & 測定**:
   * テキストエリアでMarkdownを編集し、「差分更新を実行＆測定」をクリック。
3. **外部エディタ連携**:
   * ObsidianやVSCode等の外部エディタでファイルを保存した後、「外部編集を検知」をクリック。
4. **意地悪テストプリセット**:
   * 「🔥 超長文 10,000字」「💣 特殊記号 & XSS」「📄 空ファイル」「📑 見出し乱舞」をワンクリックで注入して耐久テストが可能。
